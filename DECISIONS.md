# Decisions & Tradeoffs Log

Dated, append-only log of non-obvious calls made while building this site. See [PROJECT_PLAN.md](PROJECT_PLAN.md) for the overall architecture and [CONTENT_REVIEW.md](CONTENT_REVIEW.md) for content-specific flags.

## 2026-09-04 — Planning

**Docs-first, phased-PR delivery.** Given the size of this rebuild (new nav, modal, grid rework, two full case study pages, ~20 media assets, LinkedIn embeds), we're shipping it as five small, independently reviewable PRs instead of one large one, with `PROJECT_PLAN.md` as the standing reference so work can pick back up cleanly after a context reset.
*Why:* Kayla asked for smaller reviewable chunks and for context to survive a reset.
*How to apply:* Check `PROJECT_PLAN.md`'s phase checklist before starting new work; don't start Phase 3/4 content build-out until the asset-order mapping in `CONTENT_REVIEW.md` is confirmed.

**Reference screenshots are guidance, not source of truth.** Kayla's explicit instructions override the Figma reference images wherever they disagree (nav visibility, Table page mockup's incorrect text styles, and the three `Overlay *.png` crops being relevant only for the text-truncation behavior they demonstrate).
*Why:* the screenshots are known to be inconsistent/outdated in places.
*How to apply:* when a screenshot and a written instruction conflict, the written instruction wins; note it here if a specific conflict comes up during build.

**No build step.** Multi-file CSS/JS split (`styles/*.css`, `scripts/*.js`) instead of a bundler, loaded via plain `<link>`/`<script>` tags.
*Why:* must stay deployable as a plain GitHub Pages static site.
*How to apply:* any new dependency must be either a local file or a CDN `<script>`/`<link>` tag — no npm install / build pipeline.

**LinkedIn embeds keep native per-post iframe height.** Cards are standardized on width in the responsive grid (capped at 2 across); height stays whatever each LinkedIn embed specifies (433 / 407 / 540 for the Table page's three; 516 for Navigation's one).
*Why:* forcing a uniform height would either crop embedded content or leave large empty space, since LinkedIn's iframe embed isn't responsive-height.
*How to apply:* if this looks off once built, the alternative is a fixed-height scrollable frame per card — flag to Kayla before switching.

**Action Slot Grid prototype copied as-is; one caveat flagged, not fixed preemptively.** The prototype's `index.html` has `<base href="/app/kayla-turner-qnegow/">`, left from its original hosting environment. Not changing it up front — will verify in-browser once copied into `prototypes/action-slot-grid/` on the actual site, and only touch it if it demonstrably breaks resource loading on GitHub Pages.
*Why:* Kayla asked for the prototype to be used as-is "as much as possible."
*How to apply:* if a fix turns out to be necessary, log the exact change and reasoning here when it happens.

## 2026-09-04 — Phase 2 shipped: navigation

**Two nav behavior modes via a `[data-nav-behavior]` attribute, not two components.** `.site-nav` in `components.css` + `scripts/nav.js` handle both "reveal" (home) and "hide-on-scroll" (case study pages) from the same markup/class structure — an `IntersectionObserver` on `.site-header` drives reveal mode, a rAF-throttled scroll listener drives hide-on-scroll.
*Why:* the two behaviors share every visual detail (wordmark, links, underline states); only the trigger differs, so one component with a mode switch beats two near-duplicate ones.
*How to apply:* new pages just need `<nav class="site-nav" data-nav-behavior="reveal|hide-on-scroll">` plus (for hide-on-scroll pages) a `padding-top: calc(var(--nav-height) + ...)` on the first content block, since that mode's nav is visible from load and would otherwise cover it.

**Active link is hardcoded per page (`is-active` class in the markup), not computed from the URL.** Consistent with the rest of the site's no-build-step, no-templating approach (each page is its own static file).
*Why:* there's no templating layer to compute "current page" once and share it; hardcoding is simpler than a JS path-matching script for 3 nav links across 3 pages.
*How to apply:* any new page added to the nav needs its own copy of the nav markup with the correct link marked `is-active` — same pattern as the two case study stub pages.

**Headless screenshot testing breaks on `window.scrollTo`.** While verifying the scroll-driven nav behavior, found that Chrome's `--headless=new --screenshot=...` combo reliably returns a blank image whenever the page being captured calls `window.scrollTo` at any point (confirmed with a minimal repro completely unrelated to this site's code — even a static `<div>` disappears from the capture once a scroll call is added). Static states (nav hidden over the home hero at load, nav visible at the top of a case study page at load) screenshot fine and were verified that way.
*Why noting this:* saves re-debugging this from scratch next time a scroll-triggered feature (e.g. Phase 3/4's scroll-into-view video playback) needs visual verification — it isn't a code bug, it's this screenshot method's limitation. A real browser (manual scroll) or a CDP-based driver (Playwright/`chromium-cli`) would need to replace it for dynamic-scroll verification, and neither is installed in this dev environment.

## 2026-09-04 — Hero split + nav reveal point + return-scroll memory

**Hero description split into two elements, not one paragraph with mixed inline styles.** `.site-subtitle` (Merriweather, unchanged) for "AI-Enhanced Product and System Designer", a new `.site-tagline` (Barlow, `--text-body`/`--color-body`) for the longer explanatory line.
*Why:* Kayla wants these as two genuinely different text styles — reusing the existing body-text token for the second line keeps it consistent with every other description on the site rather than inventing a one-off style.

**Nav reveal trigger moved from the whole `.site-header` block to `.site-name` alone.** One-line change in `nav.js` (swapped the `IntersectionObserver` target). Kayla felt the transition happened too late (at the bottom of the hero/divider) and wanted it tied to the name instead.
*How to apply:* if the hero markup changes again, keep the observer pointed at whichever element should be the trigger line — it's independent of the rest of the hero's structure.

**Return-to-home scroll memory, and a real bug it surfaced.** Added: case study nav links to home set a `sessionStorage` flag before navigating; home page checks it on load and, if set, jumps straight to "nav visible, scrolled past hero" instead of resetting to the top.
*Why:* Kayla wants a visitor bouncing back from a case study to not have to re-scroll past the hero they've already seen.
*Bug caught while verifying:* the initial implementation used plain `window.scrollTo(0, y)`, which — because `html { scroll-behavior: smooth }` is set globally — animates instead of jumping instantly. That meant the restore's own scroll hadn't gone anywhere yet by the time the `IntersectionObserver`'s first callback ran, so the observer (correctly, given the still-unscrolled position) immediately stripped the `.site-nav--visible` class the restore code had just added — the net effect was the restore doing nothing. Fixed by using `window.scrollTo({ top, left: 0, behavior: 'instant' })` for this specific jump, since it's a state restore, not a scroll a visitor should watch happen.
*How to apply:* any future programmatic scroll on this site that's meant to reposition state instantly (not animate) needs the explicit `behavior: 'instant'` override — the global smooth-scroll CSS will otherwise apply to *every* `window.scrollTo`/`scrollIntoView` call, animated or not.
*Verification note:* confirmed via a debug value written into an in-flow page element rather than a screenshot — this is the third headless-screenshot quirk found this session (`window.scrollTo` degrading capture fidelity, on top of the `window.scrollTo`-causes-blank-capture and ~500px viewport-floor issues already logged above), so state-correctness checks now go through in-page text/DOM assertions instead of trusting the screenshot pixels whenever a scroll is involved.

## 2026-09-04 — Phase 3 shipped: Table Modernization case study page

**New shared files, reusable as-is for Phase 4:** `styles/case-study.css` (page template: header, sections, asset blocks, description overlay, card rows, LinkedIn grid, review-link footer, iteration modal), `scripts/overlay.js` (Read more/less), `scripts/modal.js` (open/close/focus-trap/Escape/scrim). `styles/base.css` gained `.span-3/4/6/8` grid utilities, `.text-measure` (792px prose cap, per the 8-of-12-column instruction), and `.grid-12.cards-4`/`.cards-2` responsive collapse modifiers. `.media-compare`/`.media-compare-frame` moved from `home.css` to `base.css` since the case study's top-of-page comparison video needed the same component home.css owned alone before.

**Two real bugs found and fixed while verifying, both worth remembering for Phase 4:**
1. **`[hidden]` was losing to `.btn-action`'s `display: inline-flex`.** The `Replay` buttons (`hidden` by default until a video/animation finishes) were visibly rendering anyway. Cause: an author-stylesheet class rule and the UA `[hidden]` rule sit at equal specificity, and author styles win ties regardless of which one uses an attribute selector. Fixed with an explicit `[hidden] { display: none !important; }` in `base.css`'s reset section — this protects every future `hidden`-attribute use on the site, not just Replay buttons.
2. **`<object>` elements don't size like `<img>`.** The one `<object>`-embedded animated SVG (used instead of `<img>` specifically so its playback is scriptable — see below) ignored `width:100%` and rendered at its native 1200×237 intrinsic size, overflowing its card. `<img>`/`<video>` handle `width:100%; height:auto` natively; `<object>` needs it stated explicitly (added to `.case-media object`) plus, for this specific asset, an inline `aspect-ratio: 1200/237` for reliability across engines.
*How to apply:* if Phase 4's Navigation assets include any `<object>`-embedded SVG, apply both fixes (sizing CSS + explicit aspect-ratio) up front rather than rediscovering them.

**Animated-vs-static SVG handling decided by actually checking each file, not guessing.** Grepped every Table SVG for `<animate`/`@keyframes`/`animation:` before writing markup — only `Filters-Scattered-Animation.svg` came back animated (embedded CSS `@keyframes`); the rest (Table Issues 1/3, Action Slot Grid, all six Modal assets) are static. The animated one is loaded via `<object type="image/svg+xml">` instead of `<img>` specifically so `media.js` can reach `obj.contentDocument` and pause/resume/restart its animation via an injected stylesheet — an `<img>` gives no such scripting access. Static SVGs stay plain `<img>` (simpler, no JS needed).
*Why this matters for Phase 4:* repeat the same grep check against the Navigation assets rather than assuming — do not default every SVG to `<object>` (unnecessary complexity/scripting-access risk for ones that don't need it) or every one to `<img>` (would silently break replay for an animated one).

**Replay-button reveal timing differs by asset type, intentionally.** Videos reveal Replay on their native `ended` event (fires once, exactly when playback finishes). The animated SVG has no equivalent single native event covering an arbitrary embedded `@keyframes` animation, so its Replay button is revealed immediately once the scroll-triggered play begins, not after some estimated duration. Accepted as a minor, technically-necessary inconsistency rather than over-engineering a duration-matching timer.

**Content-driven max-height (80px) for the description overlay's collapsed state, not a strict `-webkit-line-clamp`.** The overlay text is a mix of an intro paragraph and a bullet `<ul>` for design-decision sections — `line-clamp` doesn't reliably clip mixed block content the same way it clips plain text. Used `max-height` + `overflow:hidden` + a gradient-scrim fade instead, which also better matches the reference screenshots (a visual fade, not a hard mid-sentence ellipsis cut). Short single-line captions (the four "Issues discovered" items) reuse the exact same overlay component but simply omit the Read more button, since nothing is clipped for them to reveal.

**LinkedIn embeds couldn't be visually verified in this dev environment** — they render as broken-image placeholders under the offline/sandboxed headless Chrome used for screenshots (can't reach linkedin.com). The markup is the exact code Kayla supplied, unmodified beyond wrapping/sizing, so this is expected to resolve once actually served — flagging so it isn't mistaken for a real bug if seen again in this same test setup.

**Prototype's `<base href="/app/kayla-turner-qnegow/">` confirmed harmless.** Grepped the copied `index.html` for anything relying on relative resolution (only found absolute CDN URLs plus one `href="#"`) and then actually loaded the copied `prototypes/action-slot-grid/index.html` in a browser — it rendered and worked fully. No change needed; the earlier "watch item" in the Phase 0 entry is resolved.

## 2026-09-04 — Description overlay rebuilt as one page-level scrollspy bar

Kayla corrected a misreading of her original request: the description overlay was never meant to sit on each individual asset (bottom-pinned per `.case-asset-block`, as Phase 3 built it) — it's meant to be **one bar, fixed to the bottom of the viewport, whose content updates with a fade as the user scrolls through different sections.** Re-reading her original wording ("stuck to the bottom of the **screen**") confirms "screen" meant viewport, not each asset.

**Rebuilt as a scrollspy + cross-fade component**, not a per-asset one:
- Single `.description-overlay` element in the page (previously one per `.case-asset`), `position: fixed; bottom: 0`.
- Each `.case-asset` now holds its copy in a `<template class="case-asset-copy">` — inert markup, never rendered in place, just a data source `overlay.js` clones from.
- An `IntersectionObserver` with `rootMargin: '-45% 0px -45% 0px'` (shrinks the effective viewport to a thin horizontal band at vertical center) determines which `.case-asset` is "current" as the user scrolls; the bar's content swaps to match, with a ~200ms fade-out/fade-in rather than an instant swap.
- The single "View iteration examples" button lives in the bar permanently, `hidden` unless the currently active section carries `data-modal-trigger`.
*Why the `<template>` tag specifically:* it's the correct HTML primitive for "content that exists but shouldn't render where it's declared" — cleaner than a `hidden` div (which still needs to be reset/cleaned up) and avoids any risk of the per-asset copy being visible before JS runs.
*Why reset Read-more state on every section change:* an expanded state carrying over to the next section's (different, unrelated) content would be confusing — collapsed-by-default per section is the least surprising behavior.

**Verification note:** confirmed both states (bar visible with correct content over an asset; bar hidden over prose-only content) by sizing the test viewport so the target section fell within the observer's center band at page load — no `window.scrollTo` involved, sidestepping the known headless-screenshot/scroll bug from earlier. The actual cross-fade *transition* during a live scroll wasn't visually captured (would need real scroll interaction), but the underlying opacity/transform CSS transition is standard and low-risk.

## 2026-09-04 — Overlay becomes a stand-in for a real in-flow caption; video "not loading" fixed

Kayla clarified after seeing the scrollspy bar in action: the description text should live statically in the page ("stays in place once you scroll by it"), and the fixed bottom bar should only appear as a substitute for the *in-between* gap — when a tall asset (or more than one stacked under one caption) is still on screen but the real caption hasn't been scrolled to yet. Also reported videos weren't loading at all.

**Real caption + stand-in bar, not one-bar-does-everything.** `.case-asset-copy` went from an inert `<template>` (Phase 3's "one page-level bar, cross-fading between every section" model) to a real, visible, static `.case-caption` in normal flow. `.description-overlay` (the fixed bar) now only shows a *copy* of whichever caption isn't currently reachable, determined by comparing two on-screen checks per section (media block on screen AND caption NOT on screen → show the stand-in).
*Why:* matches Kayla's mental model directly — the primary reading experience is a normal in-page caption; the floating bar's whole job is covering the gap for tall/multi-asset sections, nothing more.

**Rewrote the scrollspy mechanism mid-session, from `IntersectionObserver` to manual `getBoundingClientRect()` checks on scroll/resize/`ResizeObserver`.** The first version (still using `IntersectionObserver`, just watching two elements per section instead of one) got stuck showing a stale section's caption after the real layout had already moved on. Root cause, confirmed by directly instrumenting `update()` and logging every call's actual computed geometry: **video assets resize once their metadata loads** (they start at a browser-default size before `preload="metadata"` resolves), shifting every section below them *after* `IntersectionObserver`'s first callback — and the observer wasn't reliably re-firing to correct it in this environment. Manually recomputing geometry on `scroll`, `resize`, and a `ResizeObserver` watching `document.body` (which fires on *any* reflow, including a video growing taller with no scroll involved) sidesteps the whole question of whether/when the observer decides to re-check.
*How to apply:* if another scroll-driven feature on this site needs to react to layout that can shift asynchronously after initial paint (fonts loading, images decoding, video metadata), prefer this direct-geometry-plus-`ResizeObserver` pattern over `IntersectionObserver` — it proved more predictable and easier to debug here. `nav.js`'s single-element reveal trigger is simpler and IntersectionObserver remains fine there.
*Debugging note for next time:* verifying this required instrumenting `overlay.js`'s own `update()` function directly (logging its actual internal geometry per call) rather than trusting a second, independently-written check script running "at the same time" — two separate async reads in a static test can observe genuinely different moments of an asynchronously-settling layout, which looked exactly like a stale-state bug until cross-checked against the component's own ground truth.

**Fixed videos not loading: `preload="metadata"` shows nothing until playback starts.** Browsers deliberately don't fetch/decode a frame for `preload="metadata"` — only duration and dimensions. Added a shared `paintFirstFrame(video)` helper in `media.js` that seeks to `currentTime = 0.01` once metadata loads, forcing that one frame to be fetched and painted immediately, independent of the scroll-triggered play. Applied to both `.case-media` videos and the `.media-compare` comparison videos (home page and case-study top-of-page). Also lowered the case-study video play-trigger threshold from 0.4 to 0.25 so playback starts a bit sooner.
*Why this matters:* `preload="metadata"` is still the right choice for a page with ~10 videos (avoids downloading everything eagerly) — this fix keeps that benefit while eliminating the "nothing shows up" symptom entirely.

## 2026-09-05 — Six fixes from first real-browser review

Kayla's first look in an actual browser (not headless) surfaced six issues, all fixed:

**Videos rendered far too large.** `.case-media video` had `width: 100%`, stretching every recording to the full ~1200px column width regardless of its native resolution — upscaling a smaller recording reads as oversized and soft/blurry. Changed to `width: auto; max-width: 100%` (native size, capped only so it can't overflow narrow viewports), centered. Left `<img>`/`<object>` at `width: 100%` since vector SVGs scale losslessly and the reference shows those full-bleed.

**Replay button never appeared.** Every case-study `<video>` had a `loop` attribute copied over from the home page's continuous-comparison pattern — but a looping video never fires the `ended` event, which is what reveals the Replay button and is also what "play once" depends on. Removed `loop` from `.case-media` videos (kept it on `.media-compare` videos, which are meant to loop). No JS logic changed — the button-reveal code was already correct, it just never had a trigger to run on.

**Animated SVG looped forever.** Its own embedded CSS likely specifies `infinite`; the earlier pause/resume mechanism controlled *when* it started but never touched iteration count. Added a permanent injected rule (`animation-iteration-count: 1 !important`) alongside the removable pause rule, so it always plays exactly once regardless of what its own CSS says. Removed the Replay button and all its wiring for this asset — Kayla confirmed a one-shot animation doesn't need one.

**Overlay blended into the page instead of standing out.** Replaced the gradient scrim (`rgba(...,0)` → `rgba(...,0.96)`) with a solid `var(--color-bg)` background and a `border-top`, deliberately mirroring the site nav's own solid-background-plus-border treatment rather than inventing a new visual language for it. Removed the now-unused `--overlay-scrim-from`/`--overlay-scrim-to` tokens.

**Read more showed even when there was nothing to expand.** `applySection()` now measures `textEl.scrollHeight` against the collapsed `max-height` right after setting the content, and hides the toggle button when everything already fits. Verified both ways: a short single-line caption hides it, a bulleted caption that overflows 80px shows it.

**Overlay appeared the instant an asset's top edge peeked into view.** Added a `TRIGGER_OFFSET` (100px) to the *media* visibility check only (`isMediaTriggered`) — the bar now waits until you're meaningfully into the asset before showing, rather than flashing in immediately. Kayla found this on her actual phone (headless Chrome's `--window-size` clamps below ~500px CSS width — documented earlier this session — so this specific bug was never reproducible in this environment's automated testing; the phase 5 QA pass tested down to 599px and found nothing because the bug only shows up narrower than that). She correctly self-diagnosed two of the three contributing causes before I even looked at the code.

**Root cause, confirmed by instrumenting a scratch copy of the page with injected `getBoundingClientRect()`/`scrollWidth` measurements** (same technique used earlier for asset sizing): `.ai-decision-row` is a CSS grid (`grid-template-columns: 1.2fr 1fr`), and grid items default to `min-width: auto` — meaning a track will never shrink below its content's own *min-content* size. The "View cell actions alignment decisioning prototype" button (`white-space: nowrap`, ~491px of unbreakable text) was that min-content floor for its column. On any viewport narrow enough that the column's fair-share width dropped below ~491px, the grid refused to shrink the column further, which stretched `.ai-decision-row` — and with it the shared paragraph in the *other* column, `.container`, and the page itself — wider than the actual viewport. This is exactly why the paragraph above looked too wide too, matching Kayla's own guess that "the content shares an outer container."
*Confirmed real, not just theoretical:* headless Chrome's floor prevented reproducing it below ~500px CSS width, but the same measurement script showed the button's own content width (491px, then 408px after shortening) is essentially constant regardless of container width, while the grid column's fair-share width shrinks proportionally with the viewport — meaning at a true phone width (~375-414px, well below where the button's own text stops fitting), the overflow is inevitable without a fix. The math doesn't depend on reproducing the exact pixel width to be confident in the diagnosis.

**Three-part fix, matching what Kayla asked for plus the structural guard so this class of bug can't recur:**
1. Shortened the button label: "View cell actions alignment decisioning prototype" → "View cell actions decisioning prototype" (removed "alignment," per Kayla's request) — reduces the min-content floor from ~491px to ~408px, but alone wouldn't have fully fixed it at true phone widths.
2. **`.ai-decision-row > * { min-width: 0; }`** — the actual structural fix. Lets both grid columns (the paragraph and the card) shrink to whatever width the grid assigns them, instead of being floored by their content's min-content size. This is a generically correct pattern for any CSS grid with unbreakable content in it, not a one-off hack.
3. **`.case-section-actions .btn-action` at ≤600px now also gets `white-space: normal; text-align: center;`** (alongside the existing `width: 100%; justify-content: center`) — a safety net so that even with the grid no longer forcing the page wide, the button itself can wrap onto two lines within its own now-correctly-sized card rather than spilling past its edges. Applied to the shared mobile rule (not scoped to just this button), since every other button reached by that rule has short enough text that wrapping never triggers for them — this only ever activates for a future button with an unusually long label in this slot.

**Removed the parenthetical "(which is difficult even for skilled software engineers)"** from the AI section's intro paragraph, per Kayla's request — pure copy trim, no layout effect.
